## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/chronos2_pipeline/` verbatim — seven cells tagged `metadata.dimer.embedded_module`, one per module in dependency order (`errors`, `provenance`, `config`, `model`, `validation`, `inference`, `evaluation`); the only rewrites make the default weights directory working-directory-relative and remove the package-relative `from .x import` lines, whose names the preceding cells already define. Section 3 carries the model identity and the 3-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating commit, the seven module paths, their combined SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when any carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry against the manifest **and** asserts the manifest digests equal the package's own `PINNED_*` constants; `load_pinned_model(weights_dir=WEIGHTS_DIR)` loads the verified directory through the pinned `chronos-forecasting` package without consulting the Hub for the identity (the provenance records `revision_confirmed_against_hub: false` and names the manifest as the anchor) and requests no model-repository remote code. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/chronos_2_forecasting_input_manifest.json` with the schema, ceilings, per-series observations, confirmed frequency, verdict, and one recorded rejection finding (a non-finite target); `evaluation_report` (EVAL21) writes `outputs/chronos_2_forecasting_evaluation_report.json` — `sample-sanity` with the `evaluate_forecast` metrics for Chronos-2, `last_value_baseline` and (when the 24-step hourly guard holds) `seasonal_naive_baseline` on the chronological tail holdout, `not-measurable` (with what data would make the task measurable) when no truth is supplied.
- The default sample is the repository's deterministic synthetic univariate series regenerated in code and digest-asserted against `examples/sample-data/SHA256SUMS` (no download); its metrics are sanity evidence for the input contract, the leakage boundary and the forecast path, not a correctness or benchmark claim. Primary **Mode C multi-target forecasting** executes on the default path; Mode D remains an explicit optional branch (`RUN_COVARIATE_DEMO`).
- Forecasting obligations (Notebook Specification §20.3): chronological ordering is preserved and the future is held out with no target leakage, horizon and effective context are printed, the point forecast is stated as the median, quantile semantics are stated as uncalibrated, at least one naive history-only baseline is compared, and known-future covariates are separated from future target values (Mode D refuses a target column in the future table).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog; `DIMER_BYOD_PATH` and `DIMER_RUN_COVARIATE_DEMO` are automation hooks read from the environment.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
